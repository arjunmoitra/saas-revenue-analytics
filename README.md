# saas-revenue-analytics

[![CI](https://github.com/arjunmoitra/saas-revenue-analytics/actions/workflows/ci.yml/badge.svg)](https://github.com/arjunmoitra/saas-revenue-analytics/actions/workflows/ci.yml)

A small, production-style analytics warehouse for SaaS subscription revenue, built with **dbt Core** and **DuckDB**.

It takes Stripe-style billing extracts (customers, plans, subscription versions, invoices, line items, payments), models them through a layered dbt project, and produces finance-grade metrics: MRR and its movements, ARR, churn, retention, ARPU, recognized vs billed revenue and deferred revenue. Every business rule is tested and documented, and an HTML dashboard reads only from the marts.

```
raw  ->  stg_  ->  int_  ->  dim_ / fct_  ->  metrics_  ->  dashboard
```

| | |
|---|---|
| Models | 6 staging, 8 intermediate, 9 marts (3 dims, 4 facts, 2 metric tables) |
| Tests | 344 (generic + 10 singular business-rule tests), all passing |
| Data | 600 customers, 1,080 subscription versions, 5,981 invoices, 6,332 line items, 6,746 payments, Jan 2023 to Aug 2026 |
| Stack | dbt Core 1.12, dbt-duckdb, DuckDB 1.5, Python 3.12, Plotly |

---

## 1. Business problem

A subscription business needs one trustworthy answer to questions like:

- What is our MRR and ARR right now, and how did it move this month (new, expansion, contraction, churn, reactivation)?
- Which plan tiers drive revenue and which ones churn?
- How much revenue have we actually *earned* this month, versus what we *billed*? Annual contracts paid upfront make these very different numbers.
- Which customers are growing, which are shrinking, and how well do cohorts retain?

Billing systems store the raw events for this but not the answers. Metric definitions tend to drift between spreadsheets, and nobody can explain why the finance number and the sales number disagree. This project puts the definitions in version-controlled SQL, tests them, and exposes them at a grain BI tools can use directly.

## 2. Dataset

The data is **synthetic**, generated by [`scripts/generate_synthetic_data.py`](scripts/generate_synthetic_data.py). It does not represent any real company. No public dataset exists with a coherent, relational billing chain (versioned subscriptions, invoices, line items with service periods, payment attempts and refunds), so one was generated to mimic the shape of a Stripe-style billing system. The generator is seeded, so the CSVs in `data/raw/` are reproducible byte for byte.

What makes it realistic enough to be worth modelling:

- **Subscription versioning.** Every plan, seat or billing-interval change closes the current version and opens a new one, linked by `previous_subscription_id`. Customers upgrade, downgrade, add and remove seats, switch monthly to annual, cancel, and sometimes come back.
- **Per-seat pricing across five tiers** (one retired), monthly and annual, with annual priced at ten months.
- **Invoices with line items and service periods**: subscription charges, one-time onboarding fees and discount lines. Annual plans bill twelve months at once.
- **Payments as attempts**: failed attempts, retries, partial payments, refunds, invoices that are still open, and invoices written off as uncollectible. Voided invoices are re-issued.
- **Trials** that never bill, some converting and some expiring.
- **Deliberately messy strings**: inconsistent casing, whitespace, ten spellings of "United States", `SUCCEEDED` / `Succeeded` / `succeeded`.

Raw table grains are documented in [`data/raw/README.md`](data/raw/README.md) and in the dbt source definitions.

## 4. Data model

### Staging (`models/staging/`, views)
One model per source table, same grain as the source. Only renaming, casting and cleaning: cents to dollars, ISO strings to dates, lower-cased statuses, country normalisation through the `country_codes` seed. No business logic.

### Intermediate (`models/intermediate/`, views)

| Model | Grain | Purpose |
|---|---|---|
| `int_months` | month | Date spine from Jan 2023 to the snapshot month, so quiet months still appear. |
| `int_subscription_periods` | paid subscription version | Adds plan pricing, normalised MRR, and classifies each version vs the previous one (`new`, `upgrade`, `downgrade`, `seat_expansion`, `seat_contraction`, `interval_change`, `reactivation`) using `lag()` window functions. **The single home of upgrade/downgrade logic.** |
| `int_customer_subscription_history` | customer | Lifecycle summary: first paid date, status, latest plan, counts of each change type, churn date. |
| `int_subscription_mrr_monthly` | subscription version x month | Versions active on the last day of each month, with their MRR. |
| `int_customer_mrr_monthly` | customer x month | Customer MRR by month including zero months, prior-month MRR, movement type, and signed movement amounts. |
| `int_invoice_line_totals` | invoice | Line items rolled up by type for header reconciliation. |
| `int_invoice_payments` | invoice | Charges, refunds, net collected, failed attempts, payment timing. |
| `int_revenue_recognition` | line item x service month | Daily-prorated allocation of each line to the months it was earned in. |

### Marts (`models/marts/`, tables)

| Model | Grain | What it answers |
|---|---|---|
| `dim_customers` | customer | Who they are, status, current plan and MRR, tenure, change counts, lifetime billing. |
| `dim_plans` | plan | Tier, interval, list price and per-seat monthly price. |
| `dim_subscriptions` | subscription version (incl. trials) | Every version with dates, seats, MRR, ARR and change classification. |
| `fct_invoices` | invoice | Header, line split, payments, balance due, ageing, reconciliation flag. |
| `fct_payments` | payment attempt | Charges, failures and refunds against their invoices, lateness. |
| `fct_revenue` | customer x plan x month | Recognized revenue, billed amount, collected amount and MRR side by side. |
| `fct_mrr_movements` | customer x month | The MRR waterfall at customer level with segment and plan attributes. |
| `metrics_monthly` | month | Executive KPI table (see below). |
| `metrics_monthly_by_plan` | plan tier x month | Same KPIs cut by tier, plus upgrades/downgrades into each tier. |

## 5. Key metrics

All definitions live in [`models/marts/metrics/schema.yml`](models/marts/metrics/schema.yml) next to the model and are repeated here because the assumptions matter.

| Metric | Definition | Assumptions worth knowing |
|---|---|---|
| **MRR** | Sum over paid subscription versions active on the **last day of the month** of `unit_price x seats`, with annual prices divided by 12. | Point-in-time, not an average. List price: coupons and one-time fees are excluded, so MRR can be slightly above recognized recurring revenue. Trials excluded. Past-due subscriptions stay in MRR until actually cancelled. |
| **ARR** | `MRR x 12`. | A run-rate, not a forecast and not recognized revenue. |
| **New MRR** | MRR of customers whose first paid month is this month. | A customer can be "new" only once; returning customers are reactivations. |
| **Expansion MRR** | MRR increase for customers active in both this month and last month. | Covers tier upgrades and seat additions. |
| **Contraction MRR** | MRR decrease for customers still active, as a positive number. | Covers downgrades, seat removals and monthly-to-annual switches (annual is priced lower per month). |
| **Churned MRR** | Prior-month MRR of customers whose MRR fell to zero this month. | Churn is recognised when the last paid version ends, not when the customer clicks cancel (`canceled_at` is kept for analysis). |
| **Reactivation MRR** | MRR of previously churned customers who return. | |
| **Identity** | `mrr = beginning_mrr + new + expansion + reactivation - contraction - churned` | Enforced by a singular test at customer level and checked at company level by `scripts/validate_metrics.py`. |
| **Active customers** | Customers with MRR > 0 at month end. | |
| **Customer churn rate** | `churned_customers / prior month active customers`. | |
| **ARPU** | `MRR / active customers`. | |
| **MRR growth** | `(MRR - prior MRR) / prior MRR`. | Also provided for recognized revenue. |
| **Gross / net revenue retention** | `(beginning - churn - contraction) / beginning`, net adds expansion back. | Monthly, not trailing-12. |
| **Recognized revenue** | Revenue earned in the month under the simplified revenue-recognition model below. | |
| **Deferred revenue balance** | Cumulative billed (ex-tax) minus cumulative recognized. | |

### Simplified revenue recognition

`int_revenue_recognition` spreads every invoice line evenly by day across its service period, so a $12,000 annual invoice issued on 15 March contributes about $560 to March, $1,000 to each full month, and the remainder to next March. One-time onboarding fees have a one-day service period and are recognised on the invoice date. Rounding is handled by differencing cumulative rounded shares so the monthly pieces always sum exactly to the line amount.

**This is a portfolio simplification, not ASC 606 / IFRS 15 advice.** In particular: voided invoices are excluded; uncollectible invoices are still recognised (bad debt is an expense, not a revenue reversal) and can be filtered by `invoice_status`; tax is never revenue; there are no multi-element arrangements, usage-based charges or mid-period prorations because the dataset changes plans only on period boundaries.

## 6. dbt project structure

```
saas-revenue-analytics/

├── Makefile                  # setup / data / build / validate / dashboard / docs
├── dbt_project.yml           # layer configs, as_of_date var
├── profiles.yml              # local DuckDB profile (zero setup)
├── packages.yml              # dbt_utils
├── requirements.txt
├── data/
│   ├── raw/                  # generated CSV extracts + grain documentation
│   └── saas_revenue.duckdb   # built warehouse (gitignored)
├── models/
│   ├── staging/              # stg_* + sources.yml + schema.yml
│   ├── intermediate/         # int_* + schema.yml
│   └── marts/
│       ├── core/             # dim_*
│       ├── finance/          # fct_*
│       └── metrics/          # metrics_*
├── tests/                    # singular business-rule tests
├── macros/                   # cents_to_dollars, monthly_normalized_amount,
│                             # non_negative generic test, schema naming
├── seeds/                    # country_codes lookup
├── analyses/                 # example business queries (compiled, not built)
├── scripts/                  # generate data, load raw, validate, build dashboard
└── dashboard/                # template.html + generated index.html
```

Conventions: views for staging and intermediate, tables for marts; one schema per layer (`raw`, `staging`, `intermediate`, `marts`); explicit column lists everywhere (no `select *` leaving a model); CTE names that read as steps; the snapshot date is a single `as_of_date` var; money enters as cents and is converted once by a macro.

## 7. Data quality strategy

Tests run on every layer with `dbt build`, so a failure stops downstream models from building on bad data.

**Generic tests (schema.yml)**
- `unique` + `not_null` on every primary key, and `dbt_utils.unique_combination_of_columns` on every composite-grain model (customer x month, customer x plan x month, line item x month). This is how each model's stated grain is enforced.
- `relationships` from every foreign key in facts to its dimension, and from staging back to staging, so orphan customers, plans or invoices are caught at the door.
- `accepted_values` on every status and categorical column (invoice status, payment status, movement type, change type, segment, billing interval).
- `dbt_utils.accepted_range` on seats, service days, churn rates and retention ratios.
- A custom `non_negative` generic test on every MRR, ARR, count and movement column.

**Singular tests (`tests/`)** encode the business rules a finance reviewer would check by hand:

| Test | Rule |
|---|---|
| `assert_invoice_totals_reconcile_to_line_items` | `subtotal = sum(lines)` and `total = subtotal + tax` for every invoice |
| `assert_payments_do_not_exceed_invoice_total` | charges never exceed the invoice total; refunds never exceed charges |
| `assert_subscription_end_not_before_start` | no version ends before it starts |
| `assert_subscription_versions_do_not_overlap` | a customer's paid versions are strictly sequential (overlaps would double-count MRR) |
| `assert_mrr_movements_reconcile` | the waterfall identity holds for every customer-month |
| `assert_customer_mrr_matches_subscription_mrr` | customer-level MRR equals the sum of active subscription versions |
| `assert_current_mrr_matches_latest_month` | `dim_customers.current_mrr` (computed from latest versions) agrees with `metrics_monthly.mrr` (computed via the month spine) |
| `assert_recognized_revenue_reconciles_to_line_items` | recognised revenue sums back to each line amount to the cent |
| `assert_line_item_service_period_valid` | line service periods are well formed and inside the invoice period |
| `assert_trials_never_bill` | trial versions have no invoices |

**Independent validation.** [`scripts/validate_metrics.py`](scripts/validate_metrics.py) recomputes MRR month by month for three hand-picked customers (an upgrader, a churner, an annual-plan customer), plus company MRR, ARR, ARPU and active customers, directly from the raw CSVs in pandas and compares them to the marts. It exits non-zero on any mismatch.

## 8. How to run the project locally

Requires Python 3.10+ and `make` (or run the commands inside the Makefile by hand).

```bash
git clone <this repo> && cd saas-revenue-analytics
make setup        # venv + dbt-core, dbt-duckdb, duckdb, pandas, faker, plotly + dbt deps
make data         # generate data/raw/*.csv and load them into data/saas_revenue.duckdb
make build        # dbt clean + deps + build (seeds, 23 models, 344 tests)
make validate     # independent pandas cross-check
make dashboard    # writes dashboard/index.html, open it in a browser
make docs         # dbt docs generate + serve
```

Or without make:

```bash
python3 -m venv .venv && .venv/bin/pip install -r requirements.txt
.venv/bin/python scripts/generate_synthetic_data.py
.venv/bin/python scripts/load_raw_data.py
.venv/bin/dbt deps
.venv/bin/dbt build
.venv/bin/python scripts/validate_metrics.py
.venv/bin/python scripts/build_dashboard.py
```

`profiles.yml` is checked in and points at `data/saas_revenue.duckdb`, so no `~/.dbt` configuration is needed. Query the warehouse with any DuckDB client, e.g. `duckdb data/saas_revenue.duckdb "select * from marts.metrics_monthly order by 1 desc limit 12"`.

The dashboard is a single HTML file that loads Plotly from a CDN; it needs no server. The 24-month view is the default; the time-range buttons re-render every chart, and a table view of the KPIs sits at the bottom.

## 9. What the dashboard surfaces

The data is synthetic, generated by this repo's own generator (`scripts/generate_synthetic_data.py`), so the figures below show what the models compute, not findings about a real business.

- **ARR and MRR trend together and can be read at a glance.** In the generated data, ARR reaches $8.40M (MRR $700K vs $447K a year earlier), and the models make the split between customer growth and per-customer spend visible: active customers rose from 295 to 454 while ARPU stayed near $1.5K, so `metrics_monthly` attributes the change to logo count rather than expansion.
- **Revenue concentration by tier is queryable directly from `dim_customers` and `metrics_monthly_by_plan`.** In this dataset, 47 enterprise accounts (10% of customers) carry 57% of MRR, and the top 10 accounts by ARR are 23% of the total, showing how the model supports a concentration check without a manual export.
- **Churn is broken out by plan tier and month**, so a reviewer can see whether cancellations cluster anywhere. In the generated data, trailing-twelve-month logo churn is 1.8% on Starter, 1.4% on Growth, 0.9% on Scale and 0% on Enterprise.
- **The MRR waterfall (`fct_mrr_movements`) separates new, expansion, contraction, churn and reactivation MRR each month**, and net/gross revenue retention are computed from it. Here they average 99% and 98.6% respectively, illustrating a case where expansion roughly offsets contraction and churn without exceeding it.
- **Billed and recognized revenue are computed on separate paths (`fct_invoices` vs `int_revenue_recognition`) so they can diverge when annual invoices exist.** In this dataset annual invoices are 52% of billed dollars in the trailing year, so billed revenue swings between $426K and $898K month to month while recognized revenue moves smoothly from $466K to $705K; deferred revenue (billed but not yet recognized) is tracked at $2.2M.
- **Collections risk is visible on `fct_invoices` via `invoice_status` and `balance_due`.** In the generated data, $528K sits in `uncollectible` invoices (3.3% of billed) and $171K is still `open`, showing how the model flags recognized revenue that has not been collected.

`analyses/` contains the queries behind cohort retention, the MRR waterfall, top customers by ARR, churn by reason and tier, and a worked example of one annual invoice being recognised over twelve months.

## Limitations and simplifications

Kept deliberately so the project stays readable in one sitting:

- Synthetic data, single currency (USD), no FX.
- Plan changes only on billing period boundaries, so no proration credits.
- MRR is list-price based; coupons reduce recognized revenue but not MRR.
- Revenue recognition is straight-line by day; no ASC 606 performance obligations, no bad-debt reversal.
- Retention metrics are monthly, not trailing-12 or cohort-weighted (a cohort view is in `analyses/`).
- The snapshot date is a static dbt var rather than `current_date`, so the project builds identically on any day.
- Marts are full-refresh tables; at this size incremental models would add complexity without benefit.

## What would change with real billing data

This project models a clean, fully-formed export. A real billing source (Stripe, Chargebee, an internal ledger) introduces problems the synthetic generator does not, and the pipeline would need to change to handle them:

- **Deduplication on resync.** Ingestion tools (Fivetran, Airbyte, a custom extractor) periodically resync tables and can land the same row twice, or land a row mid-update. Staging models would need a dedup step, typically `qualify row_number() over (partition by primary_key order by _loaded_at desc) = 1`, before any downstream model assumes one row per key.
- **Late-arriving records and a lookback window.** A payment or invoice can post days after the period it belongs to (a delayed webhook, a manual correction, a bank settlement lag). Incremental models built on `is_incremental()` would need a lookback window (re-processing the last N days on every run, not just the newest rows) so a late record still lands in the right month instead of being silently missed.
- **Subscription history from dbt snapshots.** This project assumes the source already exposes subscription *versions*. Most real subscription tables store only current state and overwrite it in place. Getting version history would mean running a dbt snapshot against the raw subscriptions table on every load, and rebuilding `int_subscription_periods` on top of the snapshot's `dbt_valid_from` / `dbt_valid_to` instead of a source-provided `start_date` / `end_date`.
- **Proration credits for mid-period changes.** Real billing systems let customers upgrade, downgrade or change seats mid-cycle and issue a prorated credit or charge for the partial period. This project only allows changes on period boundaries, so there are no proration line items to model. A real implementation would need a `line_type = 'proration'` case in revenue recognition, keyed to the exact days remaining in the old and new period.
- **Multiple currencies.** Every amount here is USD. A multi-currency source needs an FX rate table (by currency and date) and a decision about which rate converts a given invoice: rate at invoice date, at payment date, or at month-end for reporting, each giving a different number and each defensible for a different purpose.
- **Usage-based charges.** This dataset is pure per-seat recurring pricing. Usage-based or hybrid plans (metered API calls, tiered overages) would need a separate usage-events source, a rating step to turn usage into dollars, and a revenue-recognition rule for usage revenue, which is normally recognized as incurred rather than spread evenly like a subscription fee.
